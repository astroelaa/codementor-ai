    The core idea

    Being handed an answer is not the same as understanding

    01

    Diagnose internally, never out loud

    The mentor quietly works out what's broken. It will never show you fixed code, rewritten code, or a line-by-line correction.

    02

    One question at a time

    Small, sharp questions force you to actually read your own code — the place where real debugging skill is built.

    03

    Reasoning is graded, not results

    Your understanding meter moves when your explanation is sound, not when the code happens to run.

    04

    Explain it back or it didn't happen

    The session only closes when you describe the fix in your own words — the classic test of real comprehension.

    User flow

    From "it's broken" to "I know exactly why"

    Seven steps, every single session.

    1. 1

      Paste the code

      Drop in the function that's misbehaving.

    2. 2

      Diagnose

      The mentor reads it and prepares its first question.

    3. 3

      Reason out loud

      You answer one question at a time.

    4. 4

      Get challenged

      Weak assumptions get named as misconceptions.

    5. 5

      Spend a hint

      Stuck? Ask. You only have three, so spend them wisely.

    6. 6

      Explain your fix

      Describe the change and why it works, in your words.

    7. 7

      Follow the path

      Get a personalised list of concepts to study next.

    Key features

    Five teaching mechanics, not five chat wrappers

    🪞

    Socratic Debugging

    The mentor diagnoses the bug privately, then leads you to it with a sequence of questions. The answer is always yours.

    💡

    Hint Budget

    Three hints per session, only on request. Scarcity makes you think first — the way real debugging actually feels.

    🎭

    Misconception Detection

    "len() counts the values, not the indexes" — wrong beliefs are named the moment you express them.

    🗣️

    Explanation Check

    Before you move on, you must explain the fix in your own words. No explanation, no closure.

    📚

    Documentation Simplifier

    Sticky concept? The mentor re-explains official docs in plain language — then asks a question to check it landed.

    Architecture & tech stack

    Deliberately boring, deliberately small

    No build step, no database, no lock-in. Two folders you can read in an afternoon.

    Frontend GitHub Pages HTML · CSS · vanilla JS
    POST /api/mentor
    Backend Render (free) FastAPI · Pydantic · CORS
    HTTPS + GROQ_API_KEY
    Model Groq API Llama 3.3 70B (free tier)

    Frontend

    • Plain HTML / CSS / JS — no framework, no build
    • Single config variable for the backend URL
    • Scripted offline fallback if the API is down
    • Dark / light theme, mobile-first layout

    Backend

    • FastAPI + Pydantic request/response validation
    • GROQ_API_KEY read from environment only
    • GET /health · POST /api/mentor
    • CORS locked to GitHub Pages + local dev

    Safety & limits

    • Key never committed, never logged, never echoed
    • 3-hint budget enforced server-side
    • Timeouts + graceful 502/503 errors
    • Model falls back if the primary is rate-limited
